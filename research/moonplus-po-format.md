## 1. 格式

```
<T>*<SPINE>@<B>#<OFF>[:<PCT>%]
```

样例（实测）：

```
1785683827794*338@0#1342:28%        死人经 (冰临神下) (Z-Library).epub.po
1785683827794*40@0#240:61.2%        《拔魔》.epub.po
1785683827794*915@0#1428:66.5%      剑来 (烽火戏诸侯) (Z-Library).epub.po
1785683827794*0@0#1077858:49.99%    [活儿该][从姑获鸟开始].txt.po
```

| 字段 | 含义 | 证据强度 |
|---|---|---|
| `T` | 4 个文件取值完全相同（`1785683827794`）→ **不是**"本书进度写入时间" | 已排除 |
| `SPINE` | EPUB spine 的 **0 基索引**（TXT 书恒为 0） | **已证实** |
| `B` | 恒为 0（5/5） | 未知（§6） |
| `OFF` | 该 spine 项内的**字符偏移**（Unicode 字符计，非字节） | **已证实** |
| `PCT` | 全书进度 = **正文字符占比**（含小数，1~2 位） | **已证实** |

### `SPINE` + `OFF` 的证据

4 个样本（3 本 EPUB + 1 本 TXT）中，把 `SPINE` 当作 0 基 spine 索引、`OFF` 当作章内字符偏移，
全部落在**正文内部且语义连贯**，无一次越界：

- 拔魔：`*40#240` → `spine[40]` = 第 678 章，偏移 240 处的正文用 `moonlocate` 反查为 **239**（±1 字符）；
- 剑来：`*915#1428` → `Chapter0912.xhtml`（第 892 章）；
- 死人经：`*338#1342` → `chapter1_87.xhtml`（第 334 章）。

### `PCT` 的证据（决定性）

若 `PCT` = 全书正文字符占比：

| 书 | `.po` 报告 | 由 spine+offset 算出 | 差 |
|---|---|---|---|
| 《拔魔》 | 61.2% | 61.30% | +0.10 |
| 剑来 | 66.5% | 66.42% | −0.08 |
| 死人经 | 28% | 27.54% | −0.46 |
| 死人经（书签，独立样本） | 47.9% | 47.90% | 0.00 |

**两套互不相干的数据（`.po` 进度、`.an` 书签）都吻合，误差 < 0.5%。**
这同时排除了"按 spine 数量平均分页"的解释：那样剑来会算成 73.3%，差 6.8 个百分点。

## 2. 关键细节（会坑人的地方）

1. **`*` 是 spine 序号，不是章节号。**
   剑来 `*915` 是第 **892** 章（书前有 23 个非正文 spine 项）；死人经 `*586` 是第 **581** 章。
   两者相差数十章 —— 拿它当章号用会**系统性跑偏，且不会报错**。
2. **`OFF` 是字符数，不是字节数。** 中文 UTF-8 是 3 字节/字，按字节读会偏出 3 倍。
3. **KOReader 侧对应关系**：spine 第 N 项（0 基）= `DocFragment[N+1]`（1 基），与旧笔记一致。
4. **百分比是"字符占比"而非"字节占比"或"页数占比"**；用它在两端互推只适合显示，**不能用于精确跳转**（旧笔记这一点是对的）。
5. **总字数依赖版本**：拔魔本地这版算出 61.30%、报告 61.20%，差 0.10 个百分点 ——
   说明 Moon+ 读的那份文本比本地这份**略多约 2.5% 的字符**（同书不同制作版）。
   所以 `PCT` 只能当粗略指标，**跨版本对齐必须靠 `SPINE + OFF`，或退化为"章内百分比"**。
6. 静态检查过：这些 EPUB 没有 `linear="no"` 的 spine 项，所以 spine 计数没有"跳过非线性项"的歧义。

## 3. 意外收获：`.an` 书签文件（同样已被解开）

`.Moon+/Cache/<书名>.epub.an` 是 **zlib 压缩的纯文本**（`zlib.decompress` 即得），
结构是：`<文件字节数>` / `indent:true` / `trim:true` / `#` / 记录数 / 记录…

每条记录（换行分隔）：

```
<书名>.epub
/sdcard/Books/MoonReader/Cloud/<书名>.epub          # 原始大小写路径
/sdcard/books/moonreader/cloud/<书名>.epub          # 全小写路径（跨设备/云同步用）
586        # spine 索引（与 .po 同一套编号）
0
742        # 书签位置偏移
0
1996532479 # 三本书完全相同 → 常量，非时间戳
1791015178192   # 毫秒时间戳 = 2026-10-03（可信的写入时间）
(47.9%) 任何协议也挡不住他们的报复。” …        # 百分比 + 正文摘录
```

推断出的额外信息（对桥有用）：

- Moon+ **有云目录**：`/sdcard/Books/MoonReader/Cloud/`，并以**小写路径**做跨设备配对 ——
  和 InkBridge 用 `partialMD5` 前 8 位的思路是同一类问题的两种解法；
- `.an` 里的时间戳是**真实写入时间**，而 `.po` 的 `T` 不是 → **去重/判断新旧只能靠文件 mtime 或 ETag**，
  不能靠 `.po` 内容里的数字。

## 5. 对 InkBridge 的直接影响

- **导出（KOReader → Moon+）可行**：KOReader 有 `DocFragment[N]` 与字符偏移能力，
  换算成 `spine = N-1`、`off = 章内字符偏移` 即可写出 `.po`。**写之前必须先备份原文件。**
- **导入（Moon+ → KOReader）可行**：`spine+off` → `DocFragment[spine+1]` → xpointer，
  InkBridge 已有的"文本锚点 + 字符偏移"正好用得上。
- 因为两端都是"章内字符偏移"，**分页/滚动模式的页级精度问题不影响这条桥**（比 KOReader 之间同步还干净）。
- 跨版本失配时的降级：`SPINE` 命中但 `OFF` 越界（`moonpo.py` 会明确报
  "offset exceeds … probably a different edition"）→ 退化为"跳到该章开头"，不要硬套偏移。

## 6. 仍未确定（需要新样本，别猜）

1. **`@<B>`（5/5 都是 0）**
   可能是页码/列号/分段序号/朗读位置；也不能排除"TXT 与 EPUB 都恒为 0"（即死字段）。
   → 需要**同一本书、同一章内 `@` 非 0** 的样本，或另一台设备/另一种排版下的样本。
2. **开头大数字 `T`**
   4 个文件取值相同（`1785683827794`），而文件 mtime 各不相同 → 不是"本书的写入时间"。
   可能是设备/安装 ID、同步会话号、或某个事件时间；**在没弄清前，写 `.po` 时应原样回填**。

## 7. 结论

`.po` 的骨架 —— `spine 索引 + 章内字符偏移 + 全书字符占比` —— **已经解开并多方交叉验证**。
`SPINE`/`OFF` 的语义足以支撑双向桥；`PCT` 只适合显示。

剩下 `@` 与开头 `T` 两个字段语义未定。**但不必等它们解开**：写回时把这两个字段原样回填即可 ——
实测静读天下接受我们写出的文件并精确跳转（见 §8）。写入侧真正需要的保障不是"弄清这两个字段"，
而是 §8.6 的四道关口（换算 / 自检 / 备份 / 回读校验）。

## 8. 实装之后才知道的事（2026-10-07，双向已通）

§1–§5 是"读懂格式"的阶段。这一节是**真的把桥建起来之后**才暴露出来的东西：
三套坐标的原点不同、精度上限在哪、以及**为什么两边的页面永远不可能精确对准**。

这一节是给"以后做类似跨阅读器同步"的人写的 —— 结论都可以直接照搬，坑也都是真踩过的。

### 8.1 三套坐标，三个不同的原点（最容易误判的地方）

| 系统 | 它记的"位置"实际是什么 | 证据 |
|---|---|---|
| KOReader `doc:getXPointer()` | 当前屏幕**顶端**的那个字 | 见下面的独立验证 |
| 静读天下 `.po` 的 `OFF` | 屏幕**首行**附近 | 首行起点 +14 字（样本 A）、+33 字（样本 B） |
| KOReader 分页跳转 `GotoXPointer` | **包含该字符的那一页**的页首 | §8.2 第 2 条 |

**`getXPointer()` 是屏幕顶端** —— 与 DEVELOPMENT.md 里 KO↔KO 的实测结论一致
（"两份记录都忠实反映了各自设备屏幕顶端的位置"）。本次又独立验证了一次：

> KOReader 第 5556 页上传，插件写出 `chapter3_106` 的 `#2662`。
> 同一时刻提示框背后的正文里有「…练成之后保你经脉尽断、吐血而亡，哈哈。」，
> 它在原文中位于该章的 `#2908`。
> 若上传时屏幕顶端还是上一页的 `#2218`，一屏只装得下约 450 字 —— `#2908` **不可能**在屏幕上。
> 所以那一刻的屏幕顶端确实是 `#2662`，正好是第 5556 页的页首
> （第 5555 页覆盖 `#2218–#2661`）。

> **踩过的坑（偏移问题，值得单独记住）**：我离线预测时用的是几分钟前那张截图
> （那一页顶端是 `#2218`），而上传发生在**又翻了一页之后**（顶端 `#2662`）——
> 于是预测差了 **444 字，正好一整页**；而且它看起来"很像某种语义差异"，
> 差点被我误读成"`getXPointer()` 给的是页尾"。
>
> **教训：跨设备位置这类数据必须"同一时刻取"。** 截图 / `.po` / 日志三者时间不一致时，
> 任何离线推算都可能得出**看似合理、实则差一页**的结论。
> 唯一可靠的验证方式是：**上传之后立刻读云端那份 `.po`**（28 字节，零成本）。

### 8.2 为什么两侧页面无法精确对准（三个独立原因）

任一条单独成立，就足以让两边的页面不可能逐行对齐 —— **这不是 bug，是原理**：

1. **排版引擎不同。** KOReader 用 crengine，静读天下用自己的排版器。
   字号、行距、页边距、中文断行规则（避头尾、标点悬挂）都不同 →
   同样一段文字断行位置不同 → 页边界必然不同。**这是根本原因，任何换算都消除不了。**
2. **分页模式只能到"页"。** KOReader 的 `GotoXPointer` 在分页模式下是
   `_gotoPage(getPageFromXPointer(xp))` —— 先换算成页码，再跳到该页页首。
   即使字符偏移精确到 1 个字，落点也会被"取整"到页边界。**它是页级精度，不是字符级。**
3. **页码之间没有换算关系。** 同一本《死人经》：KOReader **8922 页**、静读天下 **8536 页** ——
   因为"页"是各自排版的产物。而且这本书有 **1222 章**，章末留白会打断"页码↔字数"的线性关系。
   实测：线性估计"KO 第 3250 页 = 全书 36.43%"，而可信窗口横跨 **60 章**（每 1% ≈ 38,663 字 ≈ 88 页）。
   **所以"按页码比例同步"这类方案一定会累积误差 —— 必须走"章节 + 章内字符偏移"。**

### 8.3 误差的实际量级（实测，不是估计）

| 方向 | 写入/读取的值 | 对方落点 | 实际误差 |
|---|---|---|---|
| 静读天下 → KOReader | `.po` `#458` | KO 该页覆盖章内 `#444–#713`，目标字在屏幕上部 | **< 1 行** |
| KOReader → 静读天下 | 写入 `#2662` | 静读天下屏首 ≈ `#2597`，目标字在屏幕 **1/4 ~ 1/3** 处 | 视口差 1/4~1/3 屏；内容上"上方多 3 行已读" |

**关键结论：误差的上限是"对方的一屏"，而不是"这本书的百分之几"。**
而且方向是可控的：写出去的是**本机的屏幕首行**，对方会落在包含它的那一页 ——
因为对方的屏通常更小，那个字会落在它屏幕的**上部**，于是"上方多出几行已读内容"当上下文，
不会跳过头（实测：目标字出现在屏幕 1/4~1/3 处，与设计预期一致）。

### 8.4 漂移风险：写"页首"会逐次后退一页，写"下一页首"才稳定

这一条是**写这份文档时才想清楚的**，也是整个互通里最隐蔽的坑。
（写 `.po` 的第一版实装写的是"当前屏幕首行"，下面会说明它为什么不稳。）

先看实测：墨桥写 `#2662` → 静读天下跳过去 → 它同步时改写成 `#2629`（它自己的屏首）。
差 33 字，看起来无害。**但把两边页宽代进去算，就会发现问题。**

设 KOReader 一页约 450 字（本书实测：第 5555 页 = `[2218, 2662)`，宽 444 字），
静读天下手机一屏约 220 字。设 KO 当前页为 `[B, B+450)`。

**写法一：写"当前页首" `B`（第一版实装的行为）**

| 步 | 发生什么 |
|---|---|
| 1 | KO 写出 `B`（它当前页的页首） |
| 2 | 静读天下跳到包含 `B` 的那一页，**它的屏首 = `B − d`**（`d` = `B` 在它那页里的偏移，实测 `d = 33`） |
| 3 | `B` 本身就是 KO 的**页边界**，所以 `B − d` 落在 KO 的**上一页**里 |
| 4 | KO 导入后跳回上一页，再写出它自己的页首 → **又退一页** |

→ **每来回一次退一页。**

**写法二：写"下一页页首" `B + 450`（正确的做法）**

| 步 | 发生什么 |
|---|---|
| 1 | KO 写出 `B + 450`（= 当前页的末尾边界 = 下一页页首） |
| 2 | 静读天下屏首 = `B + 450 − d` |
| 3 | 只要 `d < 450`（即**手机一屏比 e-ink 一页小**，通常成立），该值仍落在 **KO 的同一页**里 |
| 4 | KO 导入后停在原页，再写出同一个值 → **稳定** |

→ **稳定，而且语义正好是"接着往下读"**（对方打开就是从下一个未读处开始）。

> **判据**：写着"页边界"时,两端页宽不等必然产生 `d > 0`;
> 只有让 `d` 被"当前页的宽度"吸收掉,循环才收敛。所以**要写页尾,不能写页首。**

**修复路径已确认可行**：KOReader 有 `doc:getPageXPointer(page)`
（`frontend/document/credocument.lua:888`），可以由页码反查该页的 xpointer。于是:

```lua
local page = doc:getPageFromXPointer(doc:getXPointer())
local next_xp = doc:getPageXPointer(page + 1)   -- 下一页页首 = 本页末尾边界
```

（`page + 1` 越界时退回当前位置即可。）

**待实测确认（30 秒即可判定）**：在 KOReader 点「从静读天下读取进度」，
看它停在**第 5556 页**（推演不成立，可保持现状）还是退回**第 5555 页**（推演成立，应改成写法二）。

### 8.5 静读天下会覆盖我们写的 `.po` —— 这是正常的，不是故障

实测：我们写 `1785683827794*757@0#2662:62%`，静读天下同步后变成 `1785683827794*757@0#2629:62.0%`。

- `SPINE`（`*757`）被**完整保留** → 它接受了我们的章节定位；
- `OFF` 被换成它自己的屏首 → 正常，见 §8.1；
- `PCT` 写成 `62.0%`，而我们独立算的是 **61.9943%** → **再次印证 §1 的结论**
  （`PCT` 是**正文字符占比**），同时也说明我们算的百分比是对的。

> **所以不要把 `.po` 当成"我们写的持久记录"** —— 它每次同步都会被静读天下重写。
> 要判断新旧，只能看文件 mtime 或 ETag（同 §3）。

### 8.6 写入侧的四道关口（实测有效，可直接照搬）

改别的 App 的进度状态，必须假设自己会写错。这四道关口每一条都对应一种真实的失败：

1. **换算** —— 对不上就报错，**绝不猜一个位置**；
2. **自检** —— 让阅读器把该位置的文字报一遍，与章节正文比对。
   这是覆盖之前**唯一**能发现"两台设备上的书不是同一版本"的机会；
3. **备份** —— 原值先存到本地 `moon_backup/<文件名>.<时间>.bak`（实测两次写入留下两个 `.bak` ✓）；
4. **回读校验** —— 写完重新 GET 一次逐字比对，并如实报告是否一致。

**并且整套写回必须被 `pcall` 包住。** 我们的做法是在"上传进度成功"的回调里顺手写 `.po`，
这是为了让用户无感；代价是**写 `.po` 的任何失败都不能影响"上传成功"这个结论**。

另外，把"这次本来就不适用"和"真出问题了"分开（我们叫 `skip` / `error`）：
停在标题页或图片上时 `p[N]` 不存在，这是**正常偶发**，应当**静默跳过**；
而自检不过、拿不到账号级常量之类才是 `error`，必须让用户看见。

### 8.7 给后来者的清单

1. **不要用页码做同步。** 页是排版的产物，两端没有换算关系（§8.2 第 3 条）。
2. **`getXPointer()` 给的是屏幕顶端**（不是页尾）—— 但由此有个陷阱：
   两端页宽不等时，"写页首"会让对方回写的屏首落到你的上一页，**逐次后退一页**。
   要写"下一页页首"（§8.4）。
3. **取数据必须同一时刻。** 用几分钟前的截图去预测现在的上传，会得出差一整页、
   却看起来"像语义差异"的结论（§8.1）。**上传后立刻读云端 `.po`** 才是可靠验证。
3. **`PCT` / `:%` 不参与定位。** 实测只改它落点不变；它是正文字符占比，只用于显示。
4. **首个常量 `T` 是账号级的**，与具体书无关（4 本书同值）→ 可跨书复用，
   于是"静读天下从没打开过的书"也能生成 `.po`（已实测：《异兽迷城—澎湃》，
   云端原本没有该文件，插件新建后被静读天下一次性识别并正确跳转）。
5. **文件名 = 本机 EPUB 文件名的 basename + `.po`**（如 `死人经.epub` → `死人经.epub.po`）。
   两端必须是**同一个文件**，否则 `SPINE`/`OFF` 对不上；换算失败时要明确报错，不要乱跳。
6. **`.po` 只有 28 字节，不要去遍历云端目录。** 坚果云之类的网盘按下载量计费，
   遍历会白白消耗配额；按构造好的 URL 直接 GET 那一个文件即可。
7. **模块必须被"加载测试"覆盖。** 我们曾经把一个语法错误提交并打包出去 ——
   Lua 的长字符串 `[[...]]` 遇到内容里的 `]` 会提前闭合。
   现在每个模块都有"能不能加载 + 导出是否齐全"的断言，并且测试入口按**退出码**判定，
   把"没有输出合计"明确判为崩溃（否则崩溃的 spec 会静默通过）。
8. **`OFF` 与 `PCT` 都有"同书不同版本"的风险**：版本不同时 `OFF` 可能越界、`PCT` 会差零点几个百分点。
   跨版本对齐必须靠 `SPINE + OFF`，越界时退化为"跳到该章开头"（§5）。
